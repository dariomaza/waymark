# 22. One vocabulary, written once, and the phone's shape wins

- Status: accepted
- Date: 2026-09-24

Supersedes the arrangement ADR 20 described and did not finish: two clients
holding the same values in two files, kept in step by whoever last remembered.

## Context

The owner uses BOTH clients on the same Android phone. The PWA is installed
there and so is the APK. He put them side by side and said:

> Déjalo todo arreglado y lo más parecido posible, para que los cambios que
> vayamos haciendo vayan al mismo ritmo.

The second half of that sentence is the whole ADR. "Lo más parecido posible"
is a state, and a state can be reached once and lost the next week. "Que vayan
al mismo ritmo" is a property of the codebase, and it is the thing that was
missing.

### What was actually wrong

An audit found the two clients disagreeing about the item card's container,
its photo-box fill, its grid gaps, its name weight, its secondary size, its
initials, and its quantity badge — seven properties on the densest screen in
the product, which is a grid of these three across. It found `RowLink` and
`SearchHit` split the same way on both, which is two of the four main screens.
It found the `danger` tone filled on one client and outlined on the other,
which is Sign out, every Delete, every Revoke and every destructive line in
every menu. It found the note callout's accent edge invisible on the phone,
fields drawn on different planes, a multiline box with no minimum height, a
breadcrumb with two glyphs and two colours and no tap target on either client,
a spinner from Android beside a mark from the product, and two different ideas
about how a person leaves a dialog.

**Not one of those was wrong next to itself.** That is the important part, and
it is the same sentence this project has written before. ADR 20 found the two
icon files had drifted — the phone had an `eyeOff` the browser had never had —
and named the mechanism exactly: *"Nothing enforces that they agree... a
mistyped coordinate fails in exactly the way this codebase hates most: it does
not fail. It renders something slightly wrong, on one platform, and nobody
notices until the owner does."*

It had cost this project a root button that said "Add a room" on the browser
and "Add a unit" on the phone. Neither was wrong next to itself.

### The one part of the product that has never drifted

`packages/i18n` has two dictionaries with several hundred keys in two
languages, edited constantly, by the same people, under the same time
pressure. It has never drifted, and there is one reason:

```ts
export type Dictionary = {
  readonly [K in MessageKey]: Source[K] extends string ? string : PluralPhrase;
};
```

`Dictionary` is DERIVED from the English object. A key Spanish has not
translated is a missing property. A key Spanish invents is an excess property.
Neither compiles. Nobody has to remember anything, and nobody has ever had to.

Meanwhile `tokens.css` and `tokens.ts` held the same thirteen hex values, six
spacing steps, three radii and four type sizes, in two syntaxes, with nothing
deriving either from the other. The dictionary could not drift and the styles
could not help it. **That is not two teams with different discipline. It is
one mechanism present in one place and absent in the other.**

## Decision

### Part one: `@waymark/tokens`, and the values exist once

A new package, with zero runtime dependencies. It is NOT in `@waymark/domain`,
which also has zero and keeps them: what a box looks like is not a domain fact,
and a hex value in there is the first sentence of the argument that eventually
puts a React import in there.

The dependency runs one way and beside the others rather than through them:

```
domain  ->  api-client  ->  i18n  ->  web, mobile
tokens  ---------------------------> web, mobile
```

**The derivation is the i18n mechanism, applied to colour.** `DARK` is the
source object; `Palette` is a mapped type over its keys; `LIGHT` is declared as
a `Palette`. A scheme short one colour does not compile, and a scheme that
invents one does not either.

Each client then takes it the way its platform allows, and both are enforced:

- **The phone imports it.** `apps/mobile/src/ui/styles/tokens.ts` re-exports
  the shared objects, so a colour changed in the package is changed on the
  phone with nothing in between. A test asserts IDENTITY, not equality —
  `toBe`, not `toEqual` — because equality passes for a copy that happens to
  agree today, which is the exact state this decision exists to end. A second
  test says the file contains no hex literal at all, so the easy regression
  (somebody needs a colour in a hurry and types it there) fails on the line it
  is written.
- **The browser cannot**, because CSS cannot import TypeScript. So `tokens.css`
  is GENERATED by `cssText()` and checked in, and a test compares the file on
  disk with what the package renders, character for character. Editing the CSS
  by hand fails it; changing a value in the package without regenerating fails
  it. The fix in both directions is one command, which the failure names.

Different mechanisms, one guarantee: **the two clients cannot hold different
values and have the suite stay green.**

### The measurements are executable now

Every palette file in this product carried a block of contrast ratios in a
comment — `accent/surface 14.51`, `muted/raised 7.31`. A comment is exactly as
true as the last person to edit the value beside it. Somebody darkens the muted
ink two points to taste, the comment still says 7.98, and the number that was
evidence becomes a claim nobody can check.

So the ratios are no longer written down. They are DATA — token names and a
number — and a test recomputes every one of them from the hex values on each
run, using the WCAG 2 definition. All fourteen reproduce to the last digit,
which is the evidence that this is the same arithmetic whoever measured them
first used.

A colour that moves now either updates its own evidence or fails.

That includes the two numbers this product's trickiest decision rests on: the
lime fill has **1.26** against the light scheme's surface, and
`--color-accent-border` has **3.24**. The argument for a token that exists on
one client and not the other can now be re-run instead of believed.

### Platform-specific tokens stay expressible, and two of them exist

A shared palette is worth nothing if it makes the two clients pretend to be the
same platform. `DARK_WEB_ONLY` holds what only the browser has, and each entry
earns its place by a fact about the PLATFORM rather than about the design:

- `accentBorder`, because the light scheme's lime fill has no silhouette
  without it, and the phone has no light scheme.
- `focus`, because React Native has no `:focus-visible` and no keyboard focus
  to draw a ring around. A token for a ring nothing can draw is a colour with
  no job.

Both are **absent** from the phone rather than transparent or unused there,
which is what keeps the mobile file honest about what the platform actually
needs. `LIGHT` is likewise the SECOND SCHEME rather than "the web's palette" —
the one client that has a second scheme uses it, and nothing about it is forced
onto React Native.

### Part two: the phone's shape wins, the browser's typographic discipline wins

The owner's decision, and the reasoning is his: both clients live on a phone.
The flat-row idiom — no background, no radius, a 1px hairline between rows —
was designed for a mouse and a wide screen, and on a small dark screen it reads
as a web page wearing an app costume.

So: raised rounded rows with air between them, a bare photograph rather than a
framed tile, an outlined `danger`, a full-width primary in a sheet, one photo
per row. And every size on the scale the product publishes, which is where the
browser was the one being deliberate.

**Four rows of the audit went the other way, where the browser was right.** They
are listed because a convergence that never moves the reference client is a
convergence nobody checked:

| What | Which won | Why |
| --- | --- | --- |
| the photo box's fill | browser (`sunken`) | a photo's backing is the recess token everywhere else in this product, and the phone's own `TextField` uses it for exactly that. A raised tile there was the phone breaking a rule the rest of the app keeps. |
| a note's left edge | browser (accent) | grey on grey is a 4px stripe nobody can see. An accent edge that does not read is not a quieter accent, it is an absent one. |
| a multiline box | browser (84 minimum) | without one it is a one-line box that happens to accept newlines, which tells somebody the opposite of what it means. |
| a button's vertical padding | browser (none) | with it, a button whose label wrapped grew taller than the button beside it. A row of two peers at two heights is the one thing a row of peers must not be. |

And one went to NEITHER. The breadcrumb's tap height was 32 on the browser and
about 22 on the phone, against this product's floor of 48. Both were under it.
ADR 21 had already settled the principle for `QuietLink` — *a control may be
small to look at and may not be small to hit* — and a breadcrumb is exactly
that shape, so both are 48 now. The steps sit side by side, so the row costs 48
once rather than once per step.

### The three off-scale sizes, and the fourth that was different

The browser drew four things at sizes the browser's own scale did not contain:
`1.6rem`, `0.72rem` and `0.66rem` on the item card, and `0.7rem` in
`bottom-nav.css`.

The first three were a card written without looking at the scale. They are `xl`,
`s` and `s` now — the phone's values, all on the scale.

The fourth was a different thing and it got a different answer. **The scale
gained a fifth step, `xs: 12`.** The word under a tab-bar icon is the one place
in this product where a word is a CAPTION ON A SYMBOL rather than a line of
text: the icon carries the meaning, the word only disambiguates it, and it has
to stay on one line in two languages across four tabs on a 360px screen.
Neither client had made that decision — the browser had an unexplained 0.7rem
and the phone was inheriting React Navigation's default, which is not this
product's number to leave to a library.

12 because it EXTENDS the scale rather than sitting beside it: 14 to 16 is a
step of two, so two below 14 is where the bottom of this scale already was.

It is for that role and the guard says so: the test that holds every heading to
the scale now filters `xs` out of the sizes a heading may take, because letting
it in would quietly make 12 a legal heading — the opposite of what adding it
was for. A sentence still starts at 14.

### The sheet's footer, which was a real decision and not a number

The browser ended every sheet with a two-up row: `Cancel` beside the thing the
sheet was for, at equal width and equal weight. The phone ended every sheet
with one full-width primary and left the X in the head as the way out.

**The phone's wins.** Three arguments, and the first decides it:

1. **The way out already exists, and it is already in one place.** Every sheet
   has the X in its head; on the browser Escape also closes it and the backdrop
   is outside it. `Cancel` was a third spelling of a thing that already
   existed — and the one spelling that sits where a thumb aiming at Confirm can
   land.
2. **It halved the primary.** The sheet exists for one action. Giving away half
   the row makes "Guardar los cambios" wrap inside a 48px rectangle, which is
   the exact failure ADR 21 was written about, at two controls instead of nine.
3. **Two rectangles side by side say they are the same kind of thing**, so a
   person reads both to find out which is which. ADR 21 ruled on that already.
   `Cancel` next to `Delete` is the worst instance of it in the product: the
   two controls that must never be confused, adjacent and identical.

The forms lost `onCancel` entirely, which is the contract the phone's forms
have always had, and `units.leaveItAlone` is deleted from both dictionaries —
a key born of a row should die with the row, as this project said of
`units.showLabelPhone`.

### What stays different, on purpose

- **The selection affordance on an item card.** A checkbox top-left on the
  browser, a lime tick top-right and a 3px accent border on the phone, because
  a grid of photographs three across on a phone has no column to give.
- ~~**The avatar in the tab bar** stays a ring. Filled, at that size, in the
  accent, it reads as the selected tab whichever tab you are actually on. That
  argument is about the BAR and does not reach the 44pt disc on the account
  screen, which is filled on both now.~~

  **Not a difference any more, and for the reason it was listed as one.** It was
  here because only the phone had an avatar in a bar; the browser's lived in the
  top bar, where filled was right. The browser has the phone's bar now (see the
  amendment below), so the argument reaches it: a ring on both in the bar, a
  filled disc on both on the account screen. The exception is spent rather than
  overruled — an exception whose premise disappears should disappear with it.
- **The light scheme.** The browser follows the system; the phone does not get
  that choice, because the camera screen is black either way.
- **The photo cell's `max-width`.** One number the phone has no use for, since
  a phone is always narrower than it. It stops a desktop rendering a square
  photograph the height of the window, and both clients draw the same thing on
  the screen that matters.

### Amended: the bar, which was the loudest difference of all

- Decided by: the owner, 2026-09-24.

The audit behind this ADR compared cards, rows, fields, callouts, breadcrumbs,
spinners and sheets. It did not compare the two bottom bars, which were the
largest permanently visible object on either screen and the thing a thumb
reaches for most. The owner photographed both home screens on one phone and the
difference is unmissable:

| | browser | phone |
| --- | --- | --- |
| tabs | four | five |
| order | Places, Things, Search, Scan | Scan, Places, Search, Things, You |
| the account | an avatar in the TOP bar, opening a sheet | a destination in the bar |
| the word's weight | 650 | React Navigation's 500 |

Different count, different order, and the account reached two different ways.

**The phone's shape wins**, which is this ADR's own rule and the owner's
standing decision: both clients live on his phone. So the browser takes all of
it — five tabs, Scan first, the account as a `You` destination with the avatar
as its tab icon, and nothing in the top bar that belongs to a person.

Two decisions are overruled by that and both are amended where they live rather
than contradicted in silence:

- **`apps/mobile/src/app/navigation.ts` argued Scan is first.** That argument was
  never about React Native — "the product is a printed QR on a box and a phone
  pointed at it; every tap between launching the app and the camera being live
  is a tap taken in a garage, one-handed, holding something" — and the PWA is
  installed on the same phone. It is carried to the browser's shell unchanged.
- **`apps/web/src/app/account-sheet.tsx` argued for a sheet behind the top-bar
  avatar**, and every sentence of that argument still holds on its own terms: a
  group of controls is not a menu, and an origin with one namespace to spend
  (ADR 16) should not spend an address on two controls. It is overruled because
  it weighed ONE client. An account reached one way here and another way there
  is what the owner was looking at. The file is gone and its reasoning is at the
  top of `apps/web/src/account/account-screen.tsx`, including what the move
  costs — the address, and a navigation away from the inventory and back.

Nothing in it was lost: the language, the machine tokens (ADR 18), the passkeys
that exist only on the browser (ADR 19), "signed in as", and the way out, in the
phone's order.

The word under the icon gains the half this ADR missed. It grew the type scale a
step for that word's SIZE and left its weight to each client: 650 on one and a
library's default on the other, which is what the owner saw as one bar plainly
bolder than the other. `TAB_LABEL_WEIGHT` sits beside `TEXT.xs` now, and it is
600 — what every word inside a control in this product is set in.

## What it costs

Named, because a decision that lists no cost has not been made.

- **A shared package is a build-order dependency and one more thing to keep.**
  `@waymark/tokens` is the fifth package in the workspace and the first whose
  OUTPUT another package's source depends on. `pnpm typecheck | grep -c Done`
  prints 9 now instead of 8, and everybody who has that number memorised will
  see it change and have to find out why.
- **The browser's stylesheet is generated, and generated files are a trap.**
  Somebody will edit `tokens.css` — it is a CSS file in the place CSS files
  live — and will get a test failure about a package they have never opened.
  The banner and the failure message both name the one command that fixes it,
  and that is the whole mitigation. It is not nothing, and it is not enough:
  the honest cost is that this client now has one file that is not source.
- **A regeneration step is a step somebody forgets.** The test catches it, so
  the cost is a failed run rather than a drifted client, which is the trade
  being bought. But it is a slower loop than editing one file used to be.
- **`tsx` is a new devDependency**, for a codegen script of fifteen lines. Node
  strips types but does not resolve the `.js` specifiers `moduleResolution:
  NodeNext` requires, and the alternative was writing the generator in a way
  the rest of the workspace does not write anything.
- **The desktop got worse, twice, deliberately.** The way out of a dialog is
  now a small X in a corner rather than a button under the cursor, and somebody
  who has half-filled a form has further to travel to abandon it. And the photo
  gallery is one per row where two fitted comfortably. Both are charged to the
  screen where this app is merely also usable, and both would be wrong if that
  were the screen it was for.
- **The breadcrumb is taller.** Honouring the 48 floor on a control that used
  to be 32 adds sixteen pixels above content on every detail screen in the
  product. That is real estate somebody standing in a garage was using.
- **A source-reading guard is a blunt instrument.** The rule that no sheet
  offers a `Cancel` is enforced by reading every file that draws a sheet footer
  and asserting it does not call `t("action.cancel")`. A file that one day
  legitimately needs both a sheet footer and an unrelated cancel will fail a
  test that is technically wrong about it. That was accepted over the
  alternative, which is what the first draft did: two behavioural tests that
  covered two of seven sheets and were green with a `Cancel` sitting in a
  third.
- **A fifth tab is a narrower tab.** At 360px five destinations share the bar
  where four did, so each one is about 72px wide instead of 90. The words still
  hold on one line in both languages at `TEXT.xs`, which is the size that step
  was added for, and the tap target is the bar's full 56px height — but there is
  less slack for a sixth destination than there was, and that is the right
  amount of pressure to be under.
- **The browser gained an address it argued against.** `/you` is one more path
  in an origin the API shares (ADR 16), and one more thing `routes.test.ts` has
  to keep clear of the API's own namespace. It was refused once on exactly that
  ground, and it is spent now for a reason that ground could not weigh.
- **None of the appearance is asserted by a person looking.** Every claim in
  this ADR is a computed style or a rendered style object. A stylesheet that
  applies perfectly and looks wrong on a real 360px screen in a real garage
  passes all of it. The owner is still the only instrument for that, which is
  the same gap ADR 21 named about its tones and did not close either.

## Consequences

- `packages/tokens/src/palette.ts` is where a colour is changed. Both clients
  follow, or the build does not pass. That sentence is the deliverable; the
  rest of this file is why it was needed.
- `packages/tokens` holds two things that are not colours and belong to it for
  the same reason colours do. `TAB_LABEL_WEIGHT` sits beside `TEXT.xs`, because a
  caption on a symbol needs both halves decided in one place. `LABEL_SHEET` holds
  the printed page in millimetres, because the browser and the phone now draw the
  same sheet of labels through two different renderers (ADR 21, amended) and a
  millimetre written twice drifts exactly like a hex value written twice. Its
  four colours are deliberately NOT in `Palette`: paper is white and ink is black
  in every scheme, and a token that followed the system theme would print a grey
  square no camera can read.
- The measured contrast ratios are in `packages/tokens/src/contrast.ts` as
  data. Adding a colour pair that carries text means adding a row there, and
  the test will tell whoever changes a colour which pair they broke.
- `apps/mobile/src/ui/styles/tokens.ts` stays as the seam, holding the names
  this platform's thirty components import. It is the same arrangement ADR 20
  made for lucide behind `ui/atoms/icon.tsx`: the map's keys are ours and its
  values are somebody else's, and that is what keeps the decision reversible.
- `QuietLink` exists on both clients now, and both use it in
  `photos/views/photo-status-note.tsx` — the second site ADR 21 named for the
  shape and then deliberately left alone. That loose end is closed.
- **The one drift this ADR found and did not close is closed.** The two
  `ICON_NAMES` arrays disagreed by one name: `tags` existed on the browser and
  not on the phone, because printing was a browser errand and the phone had no
  label sheet. This file refused to fix it quietly, on the grounds that adding
  an unused name to satisfy a rule is speculative in the other direction, and
  left it for somebody to decide on purpose.

  Decided, 2026-09-24: `tags` is on both. Not to satisfy the rule — the premise
  underneath it collapsed. "Printing is a browser errand" was an assumption
  nobody had checked, `expo-print` has matched this app's SDK the whole time,
  and the phone has a label sheet now (ADR 21, amended). The name is EARNED
  here, which is exactly the test this entry said it should have to pass. The
  two arrays now differ only by `eyeOff`, which is a real platform difference:
  that reveal flips its icon and the browser's deliberately does not.
- If there is a fourth report from the owner about the two clients looking
  different, it should be read as evidence that some value is still written
  twice — and the first question is which file it is in, not which screen.
